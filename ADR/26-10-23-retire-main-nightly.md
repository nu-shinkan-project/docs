# メインリポジトリのNightly廃止とCIの責務分担

## 背景・課題

[Issue #21](https://github.com/nu-shinkan-project/nu-shinkan/issues/21)では、GitHub Actionsの複雑な対象選択・検証処理を `tools/checking` へ集約している。その過程で、メインリポジトリのNightlyも共通基盤を使う構成へ移行した。しかし、Nightlyはリポジトリセットアップの既定contextである `tooling` をTurboキャッシュの区分として使用しており、検証の目的に対応した区分になっていなかった。

Nightlyの導入背景には、docsリポジトリのADR監査のように定期実行する意味のある処理があった。一方、メインリポジトリのtest・lint・ui_test・型チェックは、基本的にコード変更に伴って必要となる。キャッシュ区分の再設計に先立ち、メインリポジトリにも定期実行を維持する必要があるかを再検討した。

現在のpreviewデプロイはPR CIを兼ねている。変更差分からapps/packagesの影響集合を求め、test・lint・ui_testを実施する。検証対象とデプロイ対象は区別されているため、デプロイ対象が存在しなくても影響パッケージがあれば検証する。`tools/` や `.github/` など、この影響集合に含まれないworkspaceのテストは、preview CIでは必ずしも実行されない。

## 判断

メインリポジトリのNightlyを廃止し、代替のCI Workflowは新設しない。検証の責務を次のように分担する。

| 対象・実行契機             | 担当する検証・処理                                                       |
| -------------------------- | ------------------------------------------------------------------------ |
| PR更新時のpreviewデプロイ  | 既存の影響集合に対するtest・lint・ui_testと、デプロイ対象のbuild・deploy |
| staging/releaseデプロイ    | 既存のデプロイ時の検証・build・deploy                                    |
| CI基盤自身の変更           | 開発者による適切なローカルテスト・型チェック・lint                       |
| mainへのpush               | 専用CIは設けない                                                         |
| メインリポジトリの定期実行 | Nightlyによる検証は行わない                                              |

具体的には次の判断を採用する。

1. メインリポジトリの `.github/workflows/nightly.yml` を削除する。定期的な検証の必要性が新たに生じた場合は、その目的から改めて設計する。
2. mainへのpushを契機に全workspaceを検証するCIを新設しない。mainへの統合結果を独立して自動検証しない制約を受け入れる。
3. previewデプロイをPR CIとして扱う。検証対象とデプロイ対象の区別を保ち、検証範囲と実行契機は変更しない。
4. CI基盤自身の専用CIは設けない。変更した開発者がローカルで検証する責任を負い、既存のテストコードと検証手段は維持する。
5. preview・staging・releaseの既存デプロイ処理を維持する。buildとdeployはデプロイパイプラインが担当し、mainへの独立したbuild検証は追加しない。
6. Nightlyで使っていた `tooling` という既定キャッシュ区分を廃止する。残る呼び出し元がcontextを明示していることを確認し、セットアップActionの既定値を削除する。指定漏れによる意図しないキーの生成を防ぐ。preview・staging・releaseのキャッシュ区分・共有方式は変更しない。

この判断はメインリポジトリを対象とする。docsリポジトリのADR監査など、独立した目的を持つ定期実行は廃止しない。

## 理由・代替案

検証の実行契機を対象の変更に対応させ、既存のpreview CIと重複するWorkflowを増やさない。CI基盤自身の品質保証はローカルで担い、その検証のためにさらにCIを追加する構成を避ける。既存のデプロイ設計が持つ検証責務を維持することで、検証対象の選択と実行の仕組みを共用できる。

検討した選択肢は次のとおり。

| 選択肢                                      | 判断と理由                                                                                                                          |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Nightlyを維持し、キャッシュ区分を再設計する | 不採用。メインリポジトリの検証に定期実行が必要である理由を十分に確認できず、区分の再設計だけでは維持目的が明確にならない。          |
| Nightlyをmain CIへ置き換える                | 不採用。統合結果と全workspaceを検証する価値はあるが、preview CIとの重複が大きく、現時点では独立したWorkflowの維持を正当化できない。 |
| CI基盤自身の検証をpreview CIへ組み込む      | 不採用。今回は既存の影響集合と検証範囲を維持し、CI基盤の検証はローカルで実施する。                                                  |
| Nightlyを廃止し、代替CIを設けない           | 採用。既存デプロイの検証と開発者のローカル検証に責務を分け、不要な定期実行とCI構成の複雑化を抑える。                                |

## 影響

メインリポジトリのWorkflowとキャッシュ既定値を整理し、関連する説明文書を実際の検証責務に合わせて更新する。既存のデプロイ設計とキャッシュ共有方式は変更しない。この判断は既存ADRの明示的な置換に当たらないため、supersedesは指定しない。

次の制約を受け入れる。

- mainへの統合結果の独立した自動検証と、Nightlyによる定期的な再検証は行われない。
- preview CIの影響集合に含まれないworkspaceは、別途自動検証されない場合がある。
- CI基盤のローカルテスト実施は開発者の責任となり、Workflowによる実施保証はない。自動実行の廃止をテスト不要という意味にはしない。

CIの構成は単純になり、必要性が確認できない定期実行を削減できる。将来、mainへの統合結果の自動検証が必要になった場合はmain CIを再検討できる。デプロイ後のintegration testにはstagingを対象とする案もあるが、その導入は将来の検討事項であり、今回の判断には含めない。
