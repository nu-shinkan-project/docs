

## 前提

本規則における「文書」とは、人間またはエージェントが継続的に参照することを目的として、プロジェクト内で恒久的に管理される Markdown 文書を指す。

一時的な作業メモ、生成物、テンプレート、テスト用データその他これに類する Markdown ファイルは、本規則における文書の分類・制限の対象としない。

## 分類

文書は、その配置方法によって次の2種類に大別する。

1. **ローカル文書**: 文書との関連が深いディレクトリに配置する文書。
2. **グローバル文書**: 特定のディレクトリの文脈ではなく、文書の役割に基づいて整理する文書。たとえば、`.agents/skills/` 配下の文書や `docs` 内の文書が該当する。

### ローカル文書

ローカル文書は、次の4種類のいずれかに分類する。

1. **説明文書**: 現状の説明やコードリーディングの補助を目的とした文書。
2. **設計文書**: 合意された決定事項、方針、構造などを明確にすることを目的とした文書。
3. **利用者向け文書**: 公開 API などの使い方や振る舞いを、その利用者に説明することを目的とした文書。
4. **ローカル指示書**: そのディレクトリに特有な、エージェントが従うべき規則を記述した文書。

### グローバル文書

グローバル文書には、たとえば次のような役割を持つものがある。

1. **ADR**: 判断とその理由を記録する文書。
2. **設計文書**: ローカルな範囲を超えて適用される、合意された設計上の決定事項を記述する文書。
3. **規約文書**: プロジェクトの開発・運用にあたって守るべき事項を記述する文書。
4. **グローバル指示書**: エージェントの判断原則や行動規範を記述する文書。

これらは代表例であり、グローバル文書の役割を網羅するものではない。具体的な役割とその運用については、後述の細則で定める。

### 呼称

文書の分類を明示する必要がない場合は、「説明書」「設計書」「マニュアル」「指示書」「ADR」「規約」「ポリシー」など、文脈に応じた自然な呼称を用いてよい。

これらの呼称と本規則上の正式な分類との対応は、厳密には定めない。

## ローカル文書の運用

### 命名規則

ローカル文書は、種類に応じて次の命名規則に従う。

* 説明文書は、ファイル名のサフィックスに `.EXPL.md` を持つ。
* 設計文書は、ファイル名のサフィックスに `.DESG.md` を持つ。
* 利用者向け文書は、ファイル名のサフィックスに `.MAN.md` を持つか、ファイル名を `README.md` とする。
* ローカル指示書は、ファイル名のサフィックスに `.INSTR.md` を持つか、ファイル名を `AGENTS.md` とする。

### 説明文書

説明文書は、現状のコードや構造を説明し、その理解を助けるための文書である。

コードと説明文書の記述が食い違う場合は、原則としてコードを正として扱う。

AI エージェントは、必要に応じて説明文書を作成・編集してよい。

説明文書には、判断、合意、規則など、その文書が削除された場合に失われてはならない情報を記載しない。

### 設計文書

設計文書は、合意された設計上の決定事項を記載する文書である。

コードと設計文書の記述が食い違う場合は、設計文書を現在有効な合意として扱い、まずコード側の不整合を疑う。

設計文書自体の変更が必要な場合は、既存の合意を暗黙に変更せず、改めて合意を得る。

AI エージェントは、ユーザから明示的な指示を受けない限り、設計文書を作成・編集しない。

設計文書は実装のあらゆる詳細を規定するためのものではない。必要以上に細かな事項を記述することは推奨しない。

### 利用者向け文書

利用者向け文書は、パッケージやコンポーネントの利用者が、その内部構造を理解しなくても利用できるようにするための文書である。

基本的には、公開 API をどのように利用するか、その操作によってどのような結果が得られるかを記述する。

パッケージやコンポーネントの大域的な位置づけや、利用に必要な概念を説明してもよい。ただし、利用に不要な内部構造の説明を主目的とはしない。

AI エージェントは、必要に応じて利用者向け文書を作成・編集してよい。

### ローカル指示書

ローカル指示書には、AI エージェント向けの指示のうち、その配置されたディレクトリ配下にのみ適用されるものを記述する。

実装上の設計方針や制約は、原則として設計文書に記述する。

ローカル指示書は、パッケージ固有のコマンドや作業手順など、その場所におけるエージェントの行動を直接制約する必要がある場合に利用する。

ローカル指示書を設計文書の代替として使用し、その内容を肥大化させない。

### ローカル文書の新設

ローカル文書を新設する場合は、前述の4分類のいずれかに分類する。

いずれの分類にも当てはまらない場合は、新しい分類を追加する前に、その内容をローカル文書として恒久的に配置する必要があるかを再検討する。

たとえば、実装計画や作業途中の検討事項など、恒久的な参照を目的としない Markdown ファイルはローカル文書として管理せず、一時作業領域や Issue などで管理する。

## グローバル文書の運用

グローバル文書については、その役割ごとに配置場所、編集権限その他必要な細則を定める。

グローバル文書の役割分類は固定しない。新たな恒久的役割が明確に必要となった場合は、既存の役割へ無理に当てはめず、必要に応じて分類を追加する。

エージェントが作業に必要なグローバル文書を発見できるよう、`AGENTS.md` にグローバル文書の参照方法を記載する。

### Front matter

グローバル文書では、文書の発見や運用に必要な metadata を YAML front matter に記述する。

文書種別ごとの必須フィールドは次のとおりとする。

| 文書種別       | 必須フィールド                                              |
| ---------- | ---------------------------------------------------- |
| ADR        | `id`, `created-at`, `relevant-to` |
| グローバル指示書   | `relevant-to`                                        |
| Snippet 文書 | `relevant-to`                                        |
| 知見文書       | `relevant-to`                                        |

#### `relevant-to`

`relevant-to` は、その文書がどのような作業、対象ファイル、ディレクトリ、技術、状況などに関連するかを示す、文書発見のための metadata である。

`relevant-to` 自体は文書の効力や適用条件を定めない。発見された文書をどのように扱うかは、その文書の種類と本文によって決まる。

`relevant-to` には、文字列または文字列のリストを指定できる。

単一の関連範囲を指定する場合:

```yaml
---
relevant-to: GitHub Actions workflows
---
```

複数の関連範囲を指定する場合:

```yaml
---
relevant-to:
  - GitHub Actions workflows
  - CI/CD related scripts
---
```

リストの各要素は OR 条件として扱い、いずれかに該当する場合はその文書を関連文書の候補として扱う。

`relevant-to` は文書を発見するための粗い情報であり、本文に必要な詳細な条件や説明を置き換えるものではない。

#### `id`

`id` は、文書を一意かつ不変に参照するための識別子である。

ID の形式自体に意味上の依存を持たせず、他の情報を ID から導出しない。

#### `created-at`

`created-at` は、文書が作成された日時を表す。

日時はタイムゾーンを含む ISO 8601 形式で記述する。

```yaml
created-at: 2026-09-13T03:45:12+09:00
```

### ADR

ADR は、判断とその理由を履歴として記録する文書である。

現在有効な設計や規則を恒久的に参照する必要がある場合は、必要に応じて設計文書、規約文書その他の適切な文書へ反映する。

AIエージェントは，必要に応じてADRを作成できる．
AIエージェントによる本文の編集は，`draft`状態かつ，セッション内で作成した場合に限り，明示的な許可を必要としない．
セッション内で作成していないADRについては，ユーザから明示的な指示がない限り，フロントマター以外は編集しない．フロントマターについては運用規則に従って更新する．

#### 設置場所

ADR は `docs/ADR/` に配置する。

#### ファイル名

ADR のファイル名は、次の形式とする。

```text
YY-MM-DD-[title].md
```

`[title]` には、内容を識別できる短い名称を使用する。

ファイル名の日付は、人間が ADR を概ね時系列で把握するために使用する。

#### front matter

##### ID

ADR の ID は、次の形式を基本とする。

```text
[branch]-YYYYMMDD-HHMMSS
```

ブランチ名は ID として利用できる形式に正規化する。

ID の形式は将来変更される可能性があるが、一度付与された ID は維持する。

##### `status`

`status` は、ADR に記録された判断の意思決定上の位置づけを表す。

次の値を使用する。

* `draft`: 採用候補として検討中の判断。
* `accepted`: 採用され、現在有効な判断。
* `rejected`: 採用候補であったが、採用されなかった判断。
* `superseded`: 一度 `accepted` となった後、別の ADR によって置き換えられた判断。

##### `audit`

`audit` は、ADR に対する機械的な整合性監査の状態を表す。

次の値を使用する。

* `pending`: 監査を待っている、または再監査が必要。
* `passed`: 監査を通過している。
* `conflict`: 他の ADR との競合など、監査上の問題が確認されている。

##### `supersedes`

ADR が既存の ADR を置き換える場合は、`supersedes` に置き換える ADR の ID をリストとして記載する。

```yaml
supersedes:
  - main-20260820-102311
```

#### 作成

新規 ADR は次の状態で作成する。

```yaml
status: draft
audit: pending
```

ADRを新規に作成する際は，`docs/templates/adr.md`の構造に従う．

基本的な状態遷移は次のとおりである。

```text
             ┌─> rejected
draft ───────┤
             └─> accepted ──> superseded
```

#### Nightly 監査

`main` 上に存在する `draft` ADR は、Nightly の ADR 監査対象とする。

監査では、少なくとも ADR 同士に意図しない競合が存在しないことを確認する。

監査を通過した `draft` ADR は、次の状態へ遷移する。

```yaml
status: accepted
audit: passed
```

競合が確認された場合は、採用候補としての状態を維持したまま監査結果を記録する。

```yaml
status: draft
audit: conflict
```

競合が解消された ADR は再び監査対象となる。

監査は ADR の整合性を確認する仕組みであり、複数の競合する判断のうちどれを採用するかは別途判断する。

#### ADR の置換

既存の `accepted` ADR を新しい判断で置き換える場合は、新しい ADR の `supersedes` に対象 ADR の ID を記載する。

新しい ADR が監査を通過して `accepted` となるとき、置き換えられる ADR は `superseded` へ遷移する。

```text
new ADR: draft    -> accepted
old ADR: accepted -> superseded
```

これにより、意図された判断の更新と、意図しない ADR 間の競合を区別する。

#### ADR の編集

`draft` ADR は、判断を検討する過程で編集する。

`accepted` ADR は、その時点で採用された判断の記録として保持する。判断を変更するときは新しい ADR を作成し、必要に応じて既存 ADR を `supersedes` によって置き換える。

ADR のライフサイクルを表す metadata は、状態遷移に応じて更新する。

### グローバル説明文書

**設置場所:** `docs/explanation/`

特定のディレクトリのローカルな文脈を超えた、現在の構造、仕組み、概念などを説明する。

グローバル説明文書は現状理解の補助を目的とし、それ自体を合意や規範の根拠とはしない。

AI エージェントは、必要に応じて作成・編集してよい。

配下のディレクトリ構造は規定しない。

### グローバル設計文書

**設置場所:** `docs/design/`

特定のディレクトリのローカルな文脈を超えて適用される、合意済みの設計上の決定事項を記述する。

ローカル設計文書と同様に、コードとの不整合がある場合は、設計文書を現在有効な合意として扱う。

AI エージェントは、ユーザから明示的な指示を受けない限り、作成・編集しない。

配下のディレクトリ構造は規定しない。

### 規約文書

**設置場所:** `docs/policy/`

プロジェクトの開発・運用にあたって、人間およびエージェントが守るべき事項を記述する。

設計文書がシステムをどのように設計するかを定めるのに対し、規約文書はプロジェクトをどのように開発・運用するかを定める。

必要に応じて、規則の理由や背景を併記してよい。

AI エージェントは、ユーザから明示的な指示を受けない限り、作成・編集しない。

配下のディレクトリ構造は規定しない。

### グローバル指示書

**設置場所:** `docs/instructions/`

グローバル指示書は、エージェントの判断原則や行動規範を記述する文書である。

人間にも適用される事項は規約文書に、設計上の決定事項は設計文書に、具体的な作業方法や手順は Skill 文書に記述し，肥大化を避けること．

AI エージェントは、ユーザから明示的な指示を受けない限り、作成・編集しない。

配下のディレクトリ構造は規定しない。

### Skill 文書

**設置場所:** `.agents/skills/`

Skill 文書は、エージェントが特定の作業を実行するための具体的な方法や手順を記述する文書である。

グローバル指示書が判断原則や行動規範を定めるのに対し、Skill 文書は特定の作業をどのように実行するかを提供する。

書式およびディレクトリ構造は、Skill の標準的な形式に従う。

AI エージェントは、ユーザから明示的な指示を受けない限り、Skill 文書を作成・編集しない。

### Snippet 文書

**設置場所:** `docs/snippets/`

Snippet 文書は、同種の実装における表現や構造のばらつきを抑えるため、標準的な実装例を示す文書である。

Snippet 文書が対象とする実装では、特段の理由がない限り、その実装例に示された構造や表現を基本形として使用する。

設計上の方針や制約そのものは設計文書または規約文書に記述し、Snippet 文書はそれらを具体的な実装の形へ落とし込むために利用する。

Snippet 文書は、実際に実装のばらつきや不必要な複雑化が問題となっている箇所に対して、必要性を確認したうえで選択的に追加する。

同じ目的に対しては、標準となる Snippet が一意に判断できる状態を保つ。

既存の Snippet に改善余地を発見した場合は、Issue を作成して変更または置換を提案する。

AI エージェントは、ユーザから明示的な指示を受けない限り、Snippet 文書を作成・編集しない。

配下のディレクトリ構造は規定しない。

Snippet 文書を新規作成する場合は，`docs/templates/snippet.md` に定める構造に従う．

### 知見文書

**設置場所:** `docs/lessons/`

知見文書は、作業を通じて得られた知見、経験則、注意事項など、将来の作業改善に役立つ情報を記録する文書である。

例えば，次の場合は知見文書の作成が適当である：

* AIエージェントがユーザからの注意を受けて修正を行った場合
* コード・技術要素に関するコストのかかる調査を行った場合

ただし，知見文書作成のタイミングは，上記の事項に限らない．

一方で，”単なる作業記録” は知見文書として適当ではない．

知見文書は規則や合意ではない。その内容が設計文書、規約文書、指示書その他の合意済み文書と食い違う場合は、これらの文書を現在有効な前提として扱う。

AI エージェントは、必要に応じて知見文書を作成・編集してよい。

知見文書を新規作成する場合は、`docs/templates/lesson.md` に定める構造に従う。

#### 再利用

エージェントは、既存の知見文書を作業に利用し、その知見が今回の作業でも有効であることを確認した場合、当該知見文書の再利用実績を更新する。

これにより、単一の事例から得られた知見と、異なる作業において繰り返し有用であることが確認された知見とを区別できるようにする。

#### 昇格

知見が異なる作業において繰り返し有用であり、より一般的な手順、規則、設計、標準実装その他の恒久的な形として扱うことが適切であると判断した場合は、適切な文書への**昇格**を検討する。

ここでいう昇格とは、知見文書の内容を Skill 文書、グローバル指示書、規約文書、設計文書、Snippet 文書その他の、より明確な役割を持つ文書へ反映することをいう。

昇格についてユーザによる判断または合意が必要な場合は、Issue を作成して昇格を提案する。

Issue には、少なくとも次の情報を記載する。

* 対象となる知見文書
* 想定する昇格先
* 昇格が適切と考える理由

配下のディレクトリ構造は規定しない。
