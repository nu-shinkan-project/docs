# 文書運用規則

## 前提

本規則における「文書」とは、人間またはエージェントが継続的に参照することを目的として、プロジェクト内で恒久的に管理される Markdown 文書を指す。

一時的な作業メモ、生成物、テンプレート、テスト用データその他これに類する Markdown ファイルは、本規則における文書の分類・制限の対象としない。

## 分類

文書は、その配置方法によって次の2種類に大別する。

1. **ローカル文書**: 文書との関連が深いディレクトリに配置する文書。
2. **グローバル文書**: 特定のディレクトリの文脈ではなく、文書の役割に基づいて整理する文書。
   たとえば、`.agents/skills/` 配下の文書や `nu-shinkan.wiki` 内の文書が該当する。

### ローカル文書

ローカル文書は、次の4種類のいずれかに分類する。

1. **説明文書**: 現状の説明やコードリーディングの補助を目的とした文書。
2. **設計文書**: 合意された決定事項、方針、構造などを明確にすることを目的とした文書。
3. **利用者向け文書**: 公開 API などの使い方や振る舞いを、その利用者に説明することを目的とした文書。
4. **ローカル指示書**: そのディレクトリに特有な、エージェントが従うべき規則を記述した文書。

### グローバル文書

グローバル文書には、たとえば次のような役割を持つものがある。

1. **ADR**: 判断とその理由を記録する文書。
2. **設計文書**: ローカルな範囲を超えて適用される、合意された設計上の決定事項を記述する文書。
3. **規約文書**: プロジェクトの開発・運用にあたって守るべき事項を記述する文書。
4. **グローバル指示書**: エージェントの判断原則や行動規範を記述する文書。

これらは代表例であり、グローバル文書の役割を網羅するものではない。具体的な役割とその運用については、後述の細則で定める。

### 呼称

文書の分類を明示する必要がない場合は、「説明書」「設計書」「マニュアル」「指示書」「ADR」「規約」「ポリシー」など、文脈に応じた自然な呼称を用いてよい。

これらの呼称と本規則上の正式な分類との対応は、厳密には定めない。

## ローカル文書の運用

### 命名規則

ローカル文書は、種類に応じて次の命名規則に従う。

* 説明文書は、ファイル名のサフィックスに `.EXPL.md` を持つこと。
* 設計文書は、ファイル名のサフィックスに `.DESG.md` を持つこと。
* 利用者向け文書は、ファイル名のサフィックスに `.MAN.md` を持つか、ファイル名を `README.md` とすること。
* ローカル指示書は、ファイル名のサフィックスに `.INSTR.md` を持つか、ファイル名を `AGENTS.md` とすること。

### 説明文書

説明文書は、現状のコードや構造を説明し、その理解を助けるための文書である。

コードと説明文書の記述が食い違う場合は、原則としてコードを正として扱う。

AI エージェントは、必要に応じて説明文書を作成・編集してよい。

説明文書には、判断、合意、規則など、その文書が削除された場合に失われてはならない情報を記載してはならない。

### 設計文書

設計文書は、合意された設計上の決定事項を記載する文書である。

コードと設計文書の記述が食い違う場合は、設計文書を現在有効な合意として扱い、まずコード側の不整合を疑うこと。

設計文書自体の変更が必要な場合は、既存の合意を暗黙に変更せず、改めて合意を得ること。

AI エージェントは、ユーザから明示的な指示を受けない限り、設計文書を作成・編集してはならない。

設計文書は実装のあらゆる詳細を規定するためのものではない。必要以上に細かな事項を記述することは推奨しない。

### 利用者向け文書

利用者向け文書は、パッケージやコンポーネントの利用者が、その内部構造を理解しなくても利用できるようにするための文書である。

基本的には、公開 API をどのように利用するか、その操作によってどのような結果が得られるかを記述する。

パッケージやコンポーネントの大域的な位置づけや、利用に必要な概念を説明してもよい。ただし、利用に不要な内部構造の説明を主目的としてはならない。

AI エージェントは、必要に応じて利用者向け文書を作成・編集してよい。

### ローカル指示書

ローカル指示書には、AI エージェント向けの指示のうち、その配置されたディレクトリ配下にのみ適用されるものを記述する。

実装上の設計方針や制約は、原則として設計文書に記述する。ローカル指示書を設計文書の代替として使用し、その内容を肥大化させてはならない。

ローカル指示書は、パッケージ固有のコマンドや作業手順など、その場所におけるエージェントの行動を直接制約する必要がある場合に設置する。

### ローカル文書の新設

ローカル文書を新設する場合は、必ず前述の4分類のいずれかに分類できなければならない。

いずれの分類にも当てはまらない場合は、新しい分類を追加するのではなく、まずその文書をローカル文書として恒久的に配置する必要があるかを再検討すること。

たとえば、実装計画や作業途中の検討事項など、恒久的な参照を目的としない Markdown ファイルはローカル文書として管理せず、一時作業領域や Issue などで管理する。

## グローバル文書の運用

グローバル文書については、その役割ごとに配置場所、編集権限その他必要な細則を定める。

グローバル文書の役割分類は固定しない。既存の役割に無理に当てはめるよりも、新たな恒久的役割が明確に必要となった場合には、必要に応じて分類を追加する。

エージェントが作業に必要なグローバル文書を発見できるよう、`AGENTS.md` から各種グローバル文書の参照方法を案内する。

エージェントは、作業に関連するグローバル指示書、規約文書および設計文書を確認する。
また、関連する知見文書が存在する場合はこれも確認し、必要に応じて説明文書、ADR、Skill 文書を参照する。

### ADR

ADR は、判断とその理由を履歴として記録するための文書である。

現在有効な設計や規則を恒久的に参照する必要がある場合は、必要に応じて設計文書、規約文書その他の適切な文書へ反映する。

#### 設置場所

ADR は `nu-shinkan.wiki/ADR/` に配置する。

#### ファイル名

ADR のファイル名は、次の形式とする。

```text
YY-MM-DD-[title].md
```

ファイル名の日付は、人間が文書を概ね時系列で把握するために使用する。

#### ID

各 ADR は、作成時に一意かつ不変な ID を付与する。

ID は次の形式を基本とする。

```text
[branch]-YYYYMMDD-HHMMSS
```

ブランチ名は ID として利用できる形式に正規化する。

ID は ADR を参照するための識別子としてのみ扱う。ID の形式は将来変更される可能性があるが、一度付与された ID は維持する。

#### Front matter

ADR は、少なくとも次の metadata を front matter に持つ。

```yaml
---
id: feature-example-20260913-034512
created-at: 2026-09-13T03:45:12+09:00
status: draft
audit: pending
---
```

`created-at` は ADR の作成日時を表し、ID とは独立した metadata として管理する。

ADR が既存の ADR を置き換える場合は、`supersedes` に対象 ADR の ID を記載する。

```yaml
---
id: feature-example-20260913-034512
created-at: 2026-09-13T03:45:12+09:00
status: draft
audit: pending
supersedes:
  - main-20260820-102311
---
```

#### Status

`status` は、その ADR に記録された判断の意思決定上の位置づけを表す。

次の状態を使用する。

* `draft`: 採用候補として検討中の判断。
* `accepted`: 採用され、現在有効な判断。
* `rejected`: 採用候補であったが、採用されなかった判断。
* `superseded`: 一度 `accepted` となった後、別の ADR によって置き換えられた判断。

新規 ADR は `draft` として作成する。

基本的な状態遷移は次のとおりである。

```text
             ┌─> rejected
draft ───────┤
             └─> accepted ──> superseded
```

#### Audit

`audit` は `status` とは独立して、ADR に対する機械的な整合性監査の状態を表す。

次の状態を使用する。

* `pending`: 監査を待っている、または再監査が必要。
* `passed`: 監査を通過している。
* `conflict`: 他の ADR との競合など、監査上の問題が確認されている。

新規 ADR は `audit: pending` として作成する。

たとえば、採用候補である ADR に競合が確認された場合は、次のように表現する。

```yaml
status: draft
audit: conflict
```

競合が解消された ADR は再び監査対象となる。

#### Nightly 監査

`main` 上に存在する `draft` ADR は、Nightly の ADR 監査対象とする。

監査では、少なくとも ADR 同士に意図しない競合が存在しないことを確認する。

監査を通過した `draft` ADR は、次の状態へ遷移する。

```yaml
status: accepted
audit: passed
```

競合が確認された場合は、採用候補としての状態を維持したまま監査結果を記録する。

```yaml
status: draft
audit: conflict
```

監査は ADR の整合性を確認する仕組みであり、複数の競合する判断のうちどれを採用するかは別途判断する。

#### ADR の置換

既存の `accepted` ADR を新しい判断で置き換える場合は、新しい ADR の `supersedes` に対象 ADR の ID を記載する。

新しい ADR が監査を通過して `accepted` となるとき、置き換えられる ADR は `superseded` へ遷移する。

```text
new ADR: draft    -> accepted
old ADR: accepted -> superseded
```

これにより、意図された判断の更新と、意図しない ADR 間の競合を区別する。

#### ADR の編集

`draft` ADR は、判断を検討する過程で編集する。

`accepted` ADR は、その時点で採用された判断の記録として保持する。
判断を変更するときは新しい ADR を作成し、必要に応じて既存 ADR を `supersedes` によって置き換える。
既存 ADR を編集してはならない．

`status`、`audit`、`supersedes` など、ADR のライフサイクルを表す metadata は、状態遷移に応じて更新する。

### グローバル説明文書

**設置場所:** `nu-shinkan.wiki/explanation/`

特定のディレクトリのローカルな文脈を超えた、現在の構造、仕組み、概念などを説明する。

グローバル説明文書は現状理解の補助を目的とし、それ自体を合意や規範の根拠とはしない。

AI エージェントは、必要に応じて作成・編集してよい。

配下のディレクトリ構造は規定しない。

### グローバル設計文書

**設置場所:** `nu-shinkan.wiki/design/`

特定のディレクトリのローカルな文脈を超えて適用される、合意済みの設計上の決定事項を記述する。

ローカル設計文書と同様に、コードとの不整合がある場合は、設計文書を現在有効な合意として扱う。

AI エージェントは、ユーザから明示的な指示を受けない限り、作成・編集してはならない。

配下のディレクトリ構造は規定しない。

### 規約文書

**設置場所:** `nu-shinkan.wiki/policy/`

プロジェクトの開発・運用にあたって、人間およびエージェントが守るべき事項を記述する。

設計文書がシステムをどのように設計するかを定めるのに対し、規約文書はプロジェクトをどのように開発・運用するかを定める。

必要に応じて、規則の理由や背景を併記してよい。

AI エージェントは、ユーザから明示的な指示を受けない限り、作成・編集してはならない。

配下のディレクトリ構造は規定しない。

### グローバル指示書

**設置場所:** `nu-shinkan.wiki/instructions/`

エージェントの判断原則や行動規範を記述する。

人間にも適用されるべき事項は、グローバル指示書ではなく規約文書に記述する。

設計上の決定事項は設計文書に、具体的な作業方法や手順は Skill 文書に記述し、グローバル指示書に過度な情報を集約しないこと。

#### 適用範囲

グローバル指示書には、その指示がどのような作業、対象ファイル、ディレクトリその他の状況に適用されるかを示す**適用範囲**を定める。

適用範囲は、エージェントが現在のタスクとその指示との関連性を判断できる内容とすること。

適用範囲は、文書の front matter に `applies-to` フィールドとして記述する。

`applies-to` には、文字列または文字列のリストを指定できる。

単一の適用範囲を指定する場合:

```yaml
---
applies-to: GitHub Actions workflows
---
```

複数の適用範囲を指定する場合:

```yaml
---
applies-to:
  - GitHub Actions workflows
  - CI/CD related scripts
---
```

`applies-to` がリストの場合、各要素はいずれか一つを満たせば適用される条件、すなわち OR 条件として扱う。

#### 編集

AI エージェントは、ユーザから明示的な指示を受けない限り、グローバル指示書を作成・編集してはならない。

配下のディレクトリ構造は規定しない。

### Skill 文書

**設置場所:** `.agents/skills/`

エージェントが特定の作業を実行するための具体的な方法や手順を記述する。

Skill 文書は行動規範を定めるものではなく、特定の作業をどのように実行するかを提供することを主目的とする。

書式およびディレクトリ構造は、Skill の標準的な形式に従う。

AI エージェントは、ユーザから明示的な指示を受けない限り、Skill 文書を作成・編集してはならない。

### 知見文書

**設置場所:** `nu-shinkan.wiki/lessons/`

知見文書は、作業を通じて得られた知見、経験則、注意事項など、将来の作業改善に役立つ情報を記録する文書である。

知見文書は規則や合意ではない。その内容が設計文書、規約文書、指示書その他の合意済み文書と食い違う場合は、これらの文書を優先する。

AI エージェントは、必要に応じて知見文書を作成・編集してよい。

#### 記載内容

知見文書には、少なくとも次の情報を記載する。

* **知見**: 作業を通じて得られた、再利用可能な知識や経験則。
* **適用範囲**: その知見が有効であると考えられる条件や状況。
* **再利用実績**: 後続の作業において、その知見が実際に利用され、有効であることが確認された記録。

必要に応じて、その知見を得るに至った背景や事例を記載してよい。

特定の事例から得られた知見を、そのまま一般則として扱ってはならない。その知見がどの範囲まで一般化できるかを考慮し、適用範囲を記述すること。

知見文書を新規作成する場合は、`nu-shinkan.wiki/templates/lesson.md` に定める構造に従うこと。

#### 再利用と昇格

エージェントは、既存の知見文書を作業に利用し、その知見が今回の作業でも有効であることを確認した場合、当該知見文書の再利用実績を更新すること。

知見が異なる作業において繰り返し有用であり、より一般的な知識、手順、規則または設計として扱うことが適切であると判断した場合は、Skill 文書、グローバル指示書、規約文書、設計文書などへの昇格を検討する。

ここでいう**昇格**とは、知見文書の内容を、より強い位置づけを持つ適切な文書へ反映することをいう。

昇格先の文書についてエージェントによる編集が制限されている場合は、エージェント自身の判断で変更せず、ユーザに昇格を提案すること。

配下のディレクトリ構造は規定しない。
