# レビュー規約

## 目的

レビューは、変更が十分に評価可能な状態にあり、その内容がプロジェクトの要求・設計・規約に適合していることを確認するために行う。

## 人間によるレビュー

変更は、原則として人間によるレビューを必要とする。

ただし、変更全体が次に掲げる事項のみから構成される場合は、人間によるレビューを省略してよい。

- プロジェクトで定められた formatter による整形その他、意味を変更しないことが明らかな機械的変更。
- 文書運用規則における次の文書に対する、意味を変更しないことが明らかな誤字、脱字、句読点または表記の修正。
  - ローカル説明文書
  - グローバル説明文書
  - 知見文書

変更がこれらの条件に該当するか明らかでない場合は、人間によるレビューを省略しない。

## レビュー段階

レビューは、次の4つの**レビュー段階**から構成する。

1. **Reviewability**
2. **Design**
3. **Implementation**
4. **Documentation**

Reviewability は、後続のレビューを信頼して行える状態にあることを確認するための段階である。

Design、Implementation、Documentation は、変更内容に該当する段階のみを適用する。すべての変更について、すべてのレビュー段階を実施する必要はない。

各レビュー段階において、質問事項または指摘事項を必ず作成する必要はない。

レビュー結果は、原則として適用したレビュー段階ごとに整理する。

Pull Request 全体を Design、Implementation、Documentation のいずれか一つに分類する必要はない。一つの Pull Request に複数の性質を持つ変更が含まれていてもよく、それぞれを該当するレビュー段階で評価する。

## レビューコメントのラベル

レビュー中に作成する質問事項または指摘事項には、次のいずれかのラベルを付す。

### `[Question]`

`[Question]` は、レビュアーが判断を完了するために追加の情報または説明を必要とするときの質問事項に用いる。

reviewee は質問に回答し、レビュアーはその回答を踏まえて再評価する。

回答の結果、問題がないと判断される場合もあれば、`[Blocking]` または `[Optional]` の指摘事項につながる場合もある。

### `[Blocking]`

`[Blocking]` は、現状のままでは変更を受け入れるべきでないとレビュアーが判断した指摘事項に用いる。

変更を受け入れる前に、この指摘事項が解消されている必要がある。

指摘事項の解消は、必ずしも特定のコード変更を意味しない。追加説明、設計の見直し、関連文書の変更その他の方法によって問題が解消される場合もある。

追加情報によって指摘の前提が誤っていたことが明らかになった場合、レビュアーは指摘を取り下げてよい。

### `[Optional]`

`[Optional]` は、問題または改善余地を指摘するものの、その対応を変更の受け入れ条件としない指摘事項に用いる。

reviewee は対応してもよく、対応しなくてもよい。

`[Optional]` の指摘事項に対する回答または修正は要求しない。

## レビューの進行

レビュー段階は、原則として Reviewability、Design、Implementation、Documentation の順に進める。

変更内容に該当しないレビュー段階は省略する。

前のレビュー段階の未解決事項に依存する部分については、その事項が解決されるまで、後続のレビュー段階で評価しない。

`[Optional]` の指摘事項は、原則として後続のレビュー段階を妨げない。

`[Question]` の質問事項への回答が後続のレビュー段階の評価に必要な場合は、回答を得て再評価するまで該当部分のレビューを保留する。

ただし、後続のレビュー段階について既に明らかな問題を発見している場合、その問題を併せて指摘することを妨げない。

## Reviewability

Reviewability では、変更内容の妥当性そのものではなく、信頼できるレビューを行える状態にあるかを評価する。

主に次の事項を確認する。

- 変更の目的および意図を理解できること。
- 変更範囲を合理的に把握できること。
- 独立した変更が不必要に混在していないこと。
- 設計変更、リファクタリング、依存関係変更、運用変更などが過度に絡み合っていないこと。
- 変更の因果関係を追跡できること。
- レビューに必要な説明、設計文書その他の関連情報が利用可能であること。
- 変更が合理的な確信をもって評価できる単位になっていること。

差分の行数のみを Reviewability の判断基準としてはならない。

大規模な機械的変更はレビュー可能な場合がある一方、小規模な変更であっても異なる関心事が複雑に絡み合っていればレビュー困難になり得る。

変更が広範、多岐、または相互に絡み合いすぎて信頼できるレビューが困難である場合、それ自体を `[Blocking]` の指摘事項としてよい。

## Design

Design では、変更の意味および方針を評価する。

主に次の事項を確認する。

- 要求を満たしていること。
- プロジェクトの既存設計と整合していること。
- 責務分割および依存方向が適切であること。
- API、データモデル、インターフェースその他の契約が適切であること。
- 互換性への影響が適切に扱われていること。
- 想定される失敗や運用上の影響が考慮されていること。
- 必要以上の複雑性を導入していないこと。
- 関連する設計文書、ADR、規約その他の合意済み事項と整合していること。

Implementation において、合意済みの設計を理由なく再審しない。

実装を通じて既存の設計上の問題が明らかになった場合は、必要に応じて Design に戻って評価する。

UI その他、実行時に利用者へ提示される文言について、その意味、意図または利用者への伝達内容を変更する場合は、Documentation ではなく Design の対象として扱う。

## Implementation

Implementation では、合意された設計および要求が適切に実現されているかを評価する。

主に次の事項を確認する。

- 実装が設計および要求と一致していること。
- 通常系および境界条件で正しく動作すること。
- エラー処理が適切であること。
- セキュリティ上の問題を導入していないこと。
- 既存動作に意図しない退行を生じさせていないこと。
- 必要なテストが存在し、変更の性質に対して適切であること。
- 運用、監視、デプロイその他の実行環境への影響が適切に扱われていること。
- 実装上の複雑性が必要以上に増加していないこと。

合意された UI 上の文言が、適切な場所および条件で利用者に提示されることの確認は Implementation の対象とする。

## Documentation

Documentation では、文書運用規則における「文書」について、その内容および管理が適切であるかを評価する。

主に次の事項を確認する。

- 記述が実際の仕様、設計または実装と整合していること。
- 文書の対象読者に必要な情報が適切に提供されていること。
- 誤解を招く記述がないこと。
- 関連する他の文書と矛盾していないこと。
- 文書が文書運用規則上の役割に適した内容となっていること。
- 分類、配置、命名その他の管理方法が文書運用規則に適合していること。

設計文書、ADR、規約その他、文書自身が設計、判断または規則を表す場合、その内容の妥当性は該当する前段階で評価し、Documentation では文書としての正確性、整合性および管理方法を評価する。

UI その他、実行時に利用者へ提示される文言は Documentation の対象としない。

## 評価できない場合

レビュアーは、特定のレビュー段階の全部または一部について十分な根拠をもって評価できない場合、その範囲を明示してよい。

これは質問事項または指摘事項ではなく、レビューの制約を示すものである。

たとえば、次のような場合がある。

- 必要な専門知識を持たない。
- 必要な文脈または情報を取得できない。
- 実行環境または外部システムを確認できない。
- 変更内容だけからは判断できない性質を持つ。

変更そのものの構成が原因で信頼できるレビューができない場合は、この扱いではなく Reviewability の問題として扱う。

## レビュアーの責任

レビュアーは、変更のあらゆる側面について必ず判断を下す責任を負わない。

一方で、自らが行った判断については、その判断を支える十分な根拠を持つ責任を負う。
