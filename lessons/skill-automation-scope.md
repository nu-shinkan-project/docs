# 既存スキルの自動化で手戻りを減らす

## 知見

既存スキルをworkflowから実行する作業では、実行方法を組み立てる前に、対象条件、処理の責務、文書の読者を揃えると手戻りを減らせる。規約や関連実装を読むだけでなく、読んだ内容から何を実装し、どこに置くかまで判断する必要がある。

### 規約は対象条件と状態遷移を続けて読む

一般的な対象指定だけで条件を確定せず、同じ節にある除外条件・再実行条件・状態遷移も読む。たとえば[文書運用規則のNightly監査](../policy/documentation.md#nightly-監査)には、draft ADRを対象とする記述の後に、競合が解消されたADRは再び監査対象となるという記述がある。前者だけから、未解消の競合ADRも毎晩再監査すると決めると、後者の条件を取り落とす。

規約の明文、そこからの解釈、ユーザが追加した条件は区別する。今回の厳密な`status: draft`かつ`audit: pending`という条件は、ユーザが明示して確定した。規約の読解だけで、この条件のすべてが明文化されていたと説明しない。

実装前に、対象となる状態、対象外の状態、再実行が可能になる条件を短く書き出す。テストの期待値も、この整理を根拠にする。誤った解釈に沿って書いたテストは通るため、テスト成功だけでは対象条件の妥当性を確認できない。

### 依頼されたファイル名から変更範囲を決めない

「workflowを修正して」という依頼でも、変更内容が監査手順そのものなら、[adr-auditスキル](../.agents/skills/adr-audit/SKILL.md)も調べる。ユーザが指定した場所は、問題の入口を示している場合がある。望む振る舞いを実現するために必要な関連箇所まで確認する。関連文書の編集権限は[文書運用規則](../policy/documentation.md)に従って確認する。

対象条件や監査手順はスキル側で管理し、workflowは定期実行、認証、スキルの呼び出し、結果の保存、Issue通知を担当する。スキルを直接呼んだ場合とworkflow経由の場合で、監査対象の判定が変わらない構成にする。スキルに対象選択処理があれば、workflowからそれを利用し、条件を別に実装しない。

### 責務を移した後は、呼び出し元に残った構造も見直す

判定処理をスキルへ移した後も、元のActionをそのまま残すと、収集・呼び出し・出力の受け渡しだけの層が残ることがある。既存のCLIを直接呼べるなら、独立したActionを維持する必要があるか再評価する。

共通利用や固有の処理を担うActionには残す理由がある。削除するかは、ファイルの数ではなく、残っている責務で判断する。[GitHub Actionsのスクリプト作例](../snippets/github_workflow_js.md)と既存CLIを確認し、単なる呼び出しのために新しい補助スクリプトを増やさない。

### 説明の必要性と文書の種類を分けて判断する

マニュアルを書く前に、誰が、何をするために読むかを決める。workflowを導入するOrganization管理者が必要とする設定と、実装を保守する開発者が知りたい内部構造は、必要な説明が異なる。

今回、workflow関連の情報を一つの文書にまとめようとして、マニュアルに内部構造の説明を追記した。しかし、[文書運用規則](../policy/documentation.md#ローカル文書の運用)では、利用方法を伝える`.MAN.md`と、現状のコードや構造の理解を助ける`.EXPL.md`は役割が異なる。話題が同じでも、既存の文書に追記する前に内容の役割を判断する必要があった。

今回の[利用設定のマニュアル](../.github/workflows.MAN.md)には、Organization側で必要なCopilot CLIの設定を残した。一方、内部の処理の流れやActionの責務など、実装の理解に必要な説明は`.EXPL.md`に配置するのが適切だった。監査条件の根拠や手順は規約・スキルに置き、説明文書から参照する。

内部構造の説明は、実装者の意図と実装を比較し、責務の重複や不要な構成を発見する助けになる。今回も、説明があったことでユーザが内部構造の不都合に気づけた。マニュアルに不要な説明だと分かったときは、説明そのものが不要なのか、配置先が違うのかを分けて判断する。説明を減らすことだけを改善の目標にしない。

### 指摘を受けたら、原因が及ぶ範囲まで修正する

対象条件の誤りを指摘されたときは、workflowのプロンプトだけでなく、スキルの説明、対象選択処理、通知対象、テストの期待値も確認する。責務を移したときは、重複した条件や不要になったActionまで整理する。指摘された一文だけを直すと、同じ原因による不整合が別の場所に残る。

初回の成果物を提出する前にも、この観点で読み合わせるとよい。今回なら、次の確認で防げた手戻りがある。

1. 監査対象を規約の一般則だけで決めず、競合後の再実行条件まで読む。
2. スキルの直接実行とworkflow経由の実行で、対象条件が一致するか確認する。
3. 追加したActionに、既存CLIの呼び出し以外の責務があるか確認する。
4. 説明の読者と用途を確認し、利用手順は`.MAN.md`、現状の構造の説明は`.EXPL.md`へ配置する。
5. テストが通ったことと、要求・規約に適合していることを分けて評価する。

## 経緯

2026年10月10日、docsリポジトリにNightlyでadr-auditを実行するworkflowを追加した。最初の成果物には、未解消の競合ADRも再監査する指示と、内部動作まで説明したマニュアルが含まれていた。

ユーザの指摘を受けて対象条件を修正したが、当初はworkflow側だけで条件を管理したため、スキルを直接呼んだ場合との不整合が残った。その後、条件と選択処理をスキルへ集約したものの、呼び出しだけを担うprepare-adr-audit Actionが残り、追加の指摘を受けて削除した。手戻りの原因は、規約の読解と責務分担の判断を成果物全体へ反映しきれなかったことにある。

マニュアルの範囲を指摘された際には、内部説明を削除する方向に偏り、`.EXPL.md`へ配置する判断が抜けていた。ユーザから、内部説明が構造上の不都合を見つける助けになったと指摘を受けた。文書の役割を混同したことと、説明自体の有用性は分けて評価する必要があった。

一方、Copilotの利用、競合時のIssue作成、作業ブランチの指定は、最初の依頼の後に追加された要件だった。これらを最初から予測すべきだったと評価することはできない。初回に完璧な成果物を保証する方法はないが、既存の規約・スキルから判断できる範囲の手戻りは、上記の確認で減らせた。実行基盤など成果物を大きく左右する選択が未指定なら、関連規約を調べながら早めに確認するとよい。

## 適用範囲

既存スキルやCLIを定期実行・CIへ組み込む作業、状態に応じて処理対象を選ぶ作業、ユーザの指摘に基づいて関連箇所を修正する作業に適用できる。

新しい要件の追加や外部サービスの仕様変更による修正まで、初回成果物の品質不足とみなすものではない。また、対象条件が実行環境ごとに意図的に異なる場合や、Actionが複数の呼び出し元で共通の責務を担う場合は、今回と同じ統合・削除が適切とは限らない。
