# デプロイ設計

## このドキュメントの目的

このドキュメントは，[デプロイのメンタルモデル](./deploy-model.md)をもとに，自動デプロイの設計を定める．用語はメンタルモデルに従う．GitHub Actionsで受け付けたデプロイ要求について，対象選定，設定・成果物の生成，反映，結果通知までの責務と入出力を扱う．現在の実装がすべてこの設計を満たすことを意味しない．

環境変数，`deployment.yaml`，設定の優先順位は，[環境設定の設計](./configuration-design.md)に従う．

## 実現方針と責務の分担

GitHub固有の処理は`.github/`配下に置き，GitHubなしに説明できるデプロイ処理は`tools/deploy/`配下のTypeScriptとして実現する．責務は実装言語ではなく，配置先と処理内容によって分ける．

| 配置先                            | 責務                                                          |
| ------------------------------ | ----------------------------------------------------------- |
| `.github/`配下のWorkflow・補助スクリプト  | イベントの解釈，起動条件・権限の確認，commitの特定，競合制御，エントリーポイントの呼び出し，GitHubへの通知 |
| `tools/deploy/`配下のCLIエントリーポイント | コマンドライン引数の受け取り，内部処理の呼び出し，最終結果に対応する終了コードでの終了                 |
| `tools/deploy/`配下の進行管理処理       | 計画・準備・実行・レポート生成の呼び出し，続行・中断の判断，各処理の結果の保持と全体結果の集約             |
| `tools/deploy/`配下の個別処理・取りまとめ処理 | パッケージの選定，sync，設定生成，テスト・ビルド・デプロイの実行とパッケージごとの結果の収集            |
| `tools/deploy/`配下のレポート生成処理     | 計画と実行結果に基づく通知用の表の組み立て，Markdownレポートの生成                       |

`tools/deploy/`は，GitHubのイベント形式，PRコメント，Job Summary，通知先，GitHub APIやGitHub固有の環境変数を知ってはならない．必要な情報は，デプロイ処理の入力として受け取る．

`.github/`配下の補助スクリプトはTypeScriptで実装してもよく，GitHub固有の知識を持ってよい．

CLIエントリーポイントはテスト対象外とし，引数と内部処理，最終結果と終了コードを接続する薄い層にとどめる．入力の検証や変換に判断が必要な場合も，そのロジックは内部処理に置く．進行管理，個別処理の取りまとめ，結果の集約，レポート生成は，CLIを起動せず関数としてテストできるようにする．この責務の分離は，ファイルの分割単位を固定するものではない．

### 処理間の連携

CLIエントリーポイントから呼び出す内部処理は，関数呼び出しと戻り値で連携する．

TypeScript内の各処理は，処理固有の判別可能なユニオン型で結果を返す．成功と，想定する失敗を戻り値の型で区別し，想定する失敗の伝達に例外の送出を用いない．共通の`Result<T, E>`やモナド的な操作，専用ライブラリの利用は前提としない．非同期処理も，想定する失敗はPromiseのrejectではなく，解決された結果の値として返す．

結果の区分は，呼び出し側の判断に必要な意味に応じて処理ごとに定める．例えばテストでは，合格，不合格，起動や結果取得などの実行エラーを区別する．各フェーズに一律の結果区分を当てはめず，フェーズ全体の結果と，その内部で得たパッケージごとの結果を区別する．

失敗時は説明用のメッセージに加え，呼び出し側の分岐や通知に必要な詳細を構造化して返す．例えば，存在しない指定パッケージは一覧として保持する．呼び出し側はメッセージを解析して処理を分岐しない．型名，プロパティ名，結果区分の具体的な文字列は実装時に定める．

フェーズ間の続行・中断は進行管理処理が，パッケージごとの実行継続や結果収集は各処理を取りまとめる内部処理が担う．進行管理処理は，想定する失敗の結果も含めて保持し，全体結果の集約とレポート生成に用いる．これらの判断をCLIエントリーポイントに置かない．

外部ライブラリ，ファイル操作，外部コマンドなどとの境界では，想定する例外や失敗をその処理の結果型へ変換する．想定外の例外は握りつぶさず，例外の内容が実行ログに残り，失敗を示す終了コードで異常終了したことが伝わるようにする．想定外の例外が発生した後の結果集約・レポート生成・復旧は要求しない．

処理の詳細はログに出力し，Workflow runから確認できるようにする．

以下の「入出力」は，各フェーズ・処理で受け渡す情報と結果の意味を定める正式な契約である．具体的なTypeScriptの型名・プロパティ名や関数の分割単位は固定しない．生成ファイルは副作用として扱い，戻り値として返す処理結果と区別する．TypeScript内では上記の戻り値の方針を用い，Workflowとの境界では既存のコマンドライン引数・レポートファイル・終了コードに対応させる．

## トリガーフェーズ

### 入出力

| 区分         | 内容                                                                       |
| ---------- | ------------------------------------------------------------------------ |
| 入力         | GitHubのイベント，自動・手動の要求内容，投稿者の権限とPR・タグに対応する情報                               |
| 受付時の出力     | channel，開始時のmode，確定した対象commit hash，modeに応じた比較元commit hash・指定パッケージ一覧・PR番号 |
| 起動しない場合の結果 | 起動条件に該当しないこと，または権限・入力・情報取得などの問題によって起動できないこととその理由                         |

### 起動条件と入力

| 契機                             | channel               | 開始時のmode                  | 対象commit              | 比較基準・指定内容     |
| ------------------------------ | --------------------- | ------------------------- | --------------------- | ------------- |
| `release`タグの付け替え               | `release`             | (`update`, `diff`)        | 新しくタグを付けたcommit       | 付け替える前のcommit |
| `staging`タグの付け替え               | `staging`             | (`update`, `diff`)        | 新しくタグを付けたcommit       | 付け替える前のcommit |
| タグの付け替えを伴わない手動実行               | `release` / `staging` | (`update`, `full`)        | 要求受付時に対応するタグが指すcommit | なし            |
| PRへのpush                       | `preview`             | (`review`, `diff`)        | PR HEAD               | PR BASE       |
| PRへの`/preview <パッケージ名...>`コメント | `preview`             | (`review`, `manual-pick`) | 要求受付時のPR HEAD         | 指定パッケージの一覧    |

対象commitと取得できる比較基準は，要求受付時にcommit hashとして確定し，実行完了まで維持する．PR BASEは要求受付時のPRのマージ先ブランチのcommitを指し，PR HEADとの共通祖先そのものではない．計画フェーズで，確定したPR BASEとPR HEADの共通祖先を求めて差分を収集する．デプロイする版はPR HEADとする．

タグ付け替え前のcommitを取得できない場合，比較元commit hashはnullとする．開始時のmodeは(`update`, `diff`)を維持し，`update.ts`を起動する．Workflow側で`full.ts`へ振り分けず，計画フェーズが比較元の欠如を検出して(`update`, `full`)へフォールバックする．

updateの差分デプロイは，比較元commitの状態がデプロイ先に反映済みであることを前提とする．デプロイ失敗・一部失敗・途中終了などによって不一致が疑われる場合は，タグの付け替えを伴わない手動実行による(`update`, `full`)を復旧経路として用いる．この経路では，要求受付時に対応するタグが指すcommitを全件デプロイする．復旧せずに後続の差分デプロイが成功しても，それだけで全体の整合が回復したとは扱わない．実際のデプロイ状態と比較元commitの不一致を自動検出する仕組みは設けない．

スラッシュコマンドの投稿者の権限確認や，PRに対応する情報の取得は`.github/`側で行う．

### エントリーポイント

Workflowは，次の情報をコマンドライン引数として各エントリーポイントへ渡す．

| mode                      | エントリーポイント                     | Workflowから渡す情報                            |
| ------------------------- | ----------------------------- | ----------------------------------------- |
| (`update`, `diff`)        | `tools/deploy/update.ts`      | channel，比較元commit hash（nullable），対象commit hash |
| (`update`, `full`)        | `tools/deploy/full.ts`        | channel，対象commit hash                     |
| (`review`, `diff`)        | `tools/deploy/review.ts`      | channel，比較元commit hash，対象commit hash，PR番号 |
| (`review`, `manual-pick`) | `tools/deploy/manual-pick.ts` | channel，指定パッケージ一覧，対象commit hash，PR番号      |

purposeとprofileはchannelから導出する．previewでは，渡されたPR番号を環境の区別に用いる．

上表はWorkflowから起動する際のmodeを示す．各CLIエントリーポイントは，対応するデプロイ要求を内部の進行管理処理へ渡す．(`review`, `diff`)からの全件収集へのフォールバックは計画処理内で行い，共通の`full`収集ロジックを利用してmodeを(`review`, `full`)とする．

### 要求の競合

同じデプロイ先を更新する要求は，Workflowの`concurrency`で直列化し，実行中の要求は完了させる．自動トリガーと手動トリガーは，同じデプロイ先について同じconcurrency groupを使用する．

| channel   | 直列化の単位       | `queue`  |
| --------- | ------------ | -------- |
| `preview` | PRごとのレビュー用環境 | `single` |
| `staging` | staging環境    | `max`    |
| `release` | release環境    | `max`    |

previewでは待機要求を最大1件にする．新しい要求が来た場合，既存の待機要求を置き換える．stagingとreleaseでは，複数の要求を待機させる．concurrencyによる厳密な実行順序の保証は追加しない．updateの反映状態に不整合が生じた場合は，手動全件デプロイを復旧経路とする．

PRクローズ時のクリーンアップも，同じPRのpreviewデプロイと同じconcurrency groupを使用し，`queue: single`で直列化する．

## 計画フェーズ

### 入出力

| 区分     | 内容                                                                              |
| ------ | ------------------------------------------------------------------------------- |
| 入力     | デプロイ要求のchannel・開始時のmode・対象commit，比較元commit（updateではnullable）または指定パッケージ一覧，必要に応じてPR番号，対象commitのワークスペース構成・依存関係・connection設定・Service Binding設定 |
| 成功時の出力 | 影響・ターゲット・ビルドパッケージの各集合，順序付きデプロイパッケージ一覧，最終mode，フォールバックした場合の理由，Service Bindingの循環などの警告                         |
| 失敗時の出力 | 計画を完了できなかった理由と，存在しない指定パッケージの一覧などの通知に必要な詳細                                       |

対象が空であることは計画の失敗とは区別し，成功結果の空集合・空一覧として表す．

### 対象選定の方針

計画フェーズでは，以下の順序で影響パッケージとターゲットパッケージを決定する．

1. selection sourceに基づいて，**起点パッケージ**を収集する．
2. 起点パッケージと，それらに直接・間接に依存するパッケージを**影響パッケージ**とする．全パッケージを起点とした場合は両者が一致するため，計算を省略する．
3. purposeが`review`の場合は，影響パッケージをもとにconnection-hydrationを行う．purposeが`update`の場合は，影響パッケージをそのまま用いる．

以上によって得られた集合を**ターゲットパッケージ**と呼ぶ．

計画フェーズの出力には，影響パッケージとターゲットパッケージの両方を保持し，準備フェーズと通知フェーズへ渡す．影響パッケージはテスト対象として用い，connection-hydrationによって置き換えない．purposeが`update`の場合は，両集合が一致する．

ターゲットパッケージのうち，ビルド対象となるものを**ビルドパッケージ**，デプロイ対象となるものを**デプロイパッケージ**と呼ぶ．`apps/`配下にあるものがデプロイパッケージであり，そのうち`package.json`に`build`スクリプトを持つものがビルドパッケージである．Turboが依存パッケージのビルドを追加実行することと，計画で選定するビルドパッケージは区別する．分類ロジックは計画処理内で共通化する．

### 1. 起点パッケージの収集

selection sourceごとの収集ロジックは，計画処理内で共通化する．

- `full`：`apps/`，`packages/`配下の全パッケージを起点パッケージとする．
- `diff`：`apps/`，`packages/`配下のパッケージのうち，コミット間の差分が存在するパッケージを起点パッケージとする．
- `manual-pick`：指定されたパッケージを起点パッケージとする．

`diff`で比較する範囲は，purposeによって次のように定める．

| purpose  | 比較する範囲                                                       | 対象選定の意図            |
| -------- | ------------------------------------------------------------ | ------------------ |
| `update` | 比較元commitと対象commitの内容を直接比較する                                 | 更新前後の変更から対象を選ぶ     |
| `review` | PR BASEとPR HEADの共通祖先からPR HEADまでを比較する（`git diff BASE...HEAD`） | PRによる変更からレビュー対象を選ぶ |

`update`では，履歴が分岐・遡行している場合も両commitの内容を直接比較し，それだけを理由とする全件収集へのフォールバックは行わない．

`review`では，前回previewをデプロイしたHEADとの差分を選定基準にしない．通常のブランチ分岐も，全件収集へのフォールバック条件にしない．mainをPRへ取り込んだ場合は，main由来の変更だけではレビュー対象を増やさず，共通祖先からPR HEADまでに残る差分から影響範囲とレビュー経路を選ぶ．選ばれたパッケージは，取り込んだmainの内容も含む現在のPR HEADで扱う．

次の場合は，selection sourceを`full`へ切り替え，共通の全件収集ロジックへフォールバックする．

- 比較に必要な履歴・比較基準を取得できない場合．`review`で共通祖先を取得できない場合も含む．
- 上記の比較範囲に`pnpm-lock.yaml`，`turbo.json`，`pnpm-workspace.yaml`のいずれかの更新が含まれる場合．

全件収集後のmodeは，purposeに応じて(`update`, `full`)または(`review`, `full`)とする．全パッケージを収集したことを後続処理へ伝え，影響パッケージの計算を省略する．purposeと対象commitは維持し，`review`では引き続きconnection-hydrationを行う．

`manual-pick`では，指定されたすべてのパッケージが実際に`apps/`，`packages/`配下に存在することを検証する．存在しないパッケージがあれば，その一覧をまとめて結果に含め，処理を中断する．`.github/`側は，その一覧とスラッシュコマンドのusageを通知する．`manual-pick`から自動フォールバックは行わない．

### 2. 影響パッケージの計算

起点パッケージと，それらに直接・間接に依存するすべての対象範囲内のワークスペースパッケージを影響パッケージとする．この計算にはTurborepoの`ls`サブコマンドを使用し，JSON形式で結果を取得する．

依存する側への拡張は，`diff`と`manual-pick`の両方に適用する．`full`，または全パッケージ収集への内部フォールバックの場合は，起点パッケージをそのまま影響パッケージとする．

ここで用いるパッケージの依存関係と，次節の実行時のconnectionは別の関係である．

### 3. connection-hydration

purposeが`review`の場合にのみ，connection-hydrationを行う．

各パッケージの[deployment.yamlで定められるconnectionとreviewEntryの設定](./configuration-design.md)をもとに，connection-graphを構築する．グラフ構築処理は，後述のデプロイ順序の決定からも利用できるよう共通化する．connection-graphは，利用元（Webなど）を始点，利用先（APIなど）を終点とする有向グラフである．

グラフの構築において，存在しないパッケージへの参照や自己ループがある場合は，それらの辺を無視する．

構築したconnection-graph上で，`reviewEntry`が`true`であるパッケージAと，影響パッケージBの組を考える．AからBへのすべての有向パスに含まれるパッケージを求め，すべての組についてその和集合をとる．この集合をターゲットパッケージとする．AとBが同じ場合は，辺を通らないパスも含め，そのパッケージ自体を対象とする．

どのreviewEntryからも到達できない影響パッケージは，ターゲットパッケージに含めない．レビューはreviewEntryを入口とする利用経路から行い，それ以外の直接的な動作確認はテストで扱う．

影響パッケージとターゲットパッケージがともに空の場合は，準備・実行を行わず，テスト・デプロイ対象がないことを通知する．ターゲットパッケージが空でも影響パッケージがある場合は，準備フェーズのsyncとテストを行い，設定生成・ビルド・デプロイは行わない．その場合も，テスト結果とデプロイ対象がないことを通知する．

### 4. デプロイ順序の決定

purposeが`update`・`review`のいずれの場合も，デプロイ対象パッケージ間のService Binding依存関係を取得し，参照先Workerを参照元Workerより先にデプロイする順序を決定する．connection-graphの構築処理を利用するが，レビュー対象選定のconnection（URL接続を含む）と，実際のデプロイ順序を制約するService Bindingは区別する．updateでもService Binding依存関係を調べるが，connection-hydrationは行わない．

循環がある場合は，該当パッケージなどを警告として保持する．循環内は任意の順序とし，循環以外の順序制約は維持する．循環だけを理由に計画を失敗させない．この順序付き一覧を実行フェーズへ，警告を通知フェーズへ渡す．

## 準備フェーズ

### 準備の進行

準備フェーズは，計画フェーズから受け取った影響パッケージとターゲットパッケージに基づいて処理する．connection-hydrationの有無を判定する必要はない．テストは影響パッケージ，デプロイ用設定の生成はターゲットパッケージ，ビルドはそのうちのビルドパッケージを対象とする．

進行管理処理は，sync・テスト・設定生成・ビルドの各結果を受け取り，影響パッケージのテストを含む必要な準備がすべて成功してから，実行フェーズへ進む．

### 1. sync

#### 入出力

| 区分     | 内容                                                     |
| ------ | ------------------------------------------------------ |
| 入力     | 対象commitのソースと環境設定                                      |
| 成功時の出力 | syncが完了したこと |
| 副作用 | 更新した環境変数・Worker名などの設定を，後続処理が参照するファイルへ反映する |
| 失敗時の出力 | syncを完了できなかった理由と，通知に必要な詳細                              |

#### 処理方針

syncは既存設定の同期・最新化を担当する．デプロイ用コンフィグアーティファクトの生成は，後続の設定生成処理が担当する．syncを実行し，環境変数やWorker名を最新化する．失敗した場合は，後続処理を中断し，結果を通知する．

### 2. テスト

#### 入出力

| 区分         | 内容                                                              |
| ---------- | --------------------------------------------------------------- |
| 入力         | テスト対象の影響パッケージ，対象commitのソースと依存関係，sync後の設定，テスト・キャッシュの実行条件         |
| パッケージごとの出力 | 合格・不合格・実行エラー・テストなしの区別，通知に必要な結果の要約・詳細，キャッシュ利用の有無．実行エラーの場合はその理由と取得できた詳細 |

テストの取りまとめ処理は，Turboを通じた影響パッケージの逐次実行と結果収集を行い，`test`スクリプトがなければ「テストなし」を記録する．Turboの実行情報から，パッケージごとの合格・不合格・実行エラーを取得する．取りまとめ処理は，本節の規則に従って残りのテストを続行し，進行管理処理が集約された結果から設定生成以降へ進めるかを判断する．通知上の「対象外」「未実行」は，レポート生成処理が計画と実行結果から判定する．

#### 処理方針

影響パッケージについて，`test`スクリプトがあれば実行する．スクリプトがない場合は，テストなしとして記録し，そのパッケージについては後続処理へ進む条件を満たしたものとする．

ターゲットパッケージに含まれない影響パッケージもテスト対象とする．ターゲットパッケージにのみ含まれるパッケージは，テスト対象外とする．

1回のデプロイ処理内では，Turborepoを通じて影響パッケージの`test`スクリプトを1パッケージずつ逐次実行する．Turboの並列度制限と失敗時の継続オプションを利用し，タスク依存関係によって意図しないパッケージのテストが実行されないようにする．パッケージ内部の並列化は，各パッケージのテスト設定に委ねる．パッケージ間の逐次実行は，各パッケージが単独実行時に想定する以上の負荷が重なり，リソース競合によるタイムアウトなどでテスト結果が不安定になることを抑えるためである．

失敗したパッケージがあっても，残りの影響パッケージのテストを行い，結果をまとめる．一つでも失敗した場合は，そのパッケージがターゲットパッケージに含まれるかどうかによらず，設定生成・ビルド・デプロイへ進まない．ターゲットパッケージが空の場合も，テストの失敗は処理全体の失敗として扱う．

テスト結果の再利用は，Turborepoのキャッシュで実現できる範囲とする．繰り返しpushした際に，同じ入力のテストを何度も実行しないことを目的とし，成功・失敗の両方を再利用する独自の仕組みは設けない．

通知に必要なテスト結果は，成否によらず戻り値に含め，進行管理処理が保持してレポート生成処理へ渡す．キャッシュを利用した場合も，通知に必要な結果を取得し，同じ戻り値の形式で返す．

結果の取得にはTurboの機械可読な実行情報などを利用し，キャッシュヒット時も同じ形式で通知に必要な結果を取得できるようにする．結果ファイルの生成自体は契約としない．

#### テストキャッシュ

GitHub ActionsとTurborepoの二段階でキャッシュする．Workflow run間の保存・復元は`.github/`側のGitHub Actionsが，各テストのキャッシュ判定と結果再利用はTurborepoが担当する．テスト結果に影響する入力をTurboのキャッシュ判定に含める．

キャッシュの名前空間は，previewではPRごと，stagingとreleaseではchannelごとに分離する．保存キーにはrun IDとrun attemptなど実行ごとに異なる識別情報を含め，同じcommitの再実行でも新しく保存できるようにする．復元時は同じ名前空間のキーを前方一致で探索し，最新の過去キャッシュを利用する．なお，技術的課題によりキャッシュが共有できない事由が存在する場合，回避に複雑な手法を必要とする場合はキャッシュの利用を断念する．キャッシュはあくまで高速化の手段に過ぎないことに留意せよ．

復元に失敗した場合は通常どおりテストを実行する．保存に失敗してもテストの成否を変更しない．一部のテストが失敗した場合も，成功したテストのキャッシュを保存できるようにする．想定外の異常終了やキャンセル時の保存までは保証しない．

### 3. デプロイ用設定の生成

#### 入出力

| 区分     | 内容                                                                               |
| ------ | -------------------------------------------------------------------------------- |
| 入力     | ターゲットパッケージ集合，sync後のネイティブな設定とconnection設定，channelとそこから導出するprofile，previewの場合はPR番号 |
| 成功時の出力 | 必要な設定生成が完了したこと |
| 副作用 | 各パッケージの所定の場所にコンフィグアーティファクトを生成する |
| 失敗時の出力 | 設定生成に失敗した理由と，該当パッケージなどの詳細                                                        |

ネイティブな設定ファイルがなく生成対象にならない場合は，生成物がないことを失敗とは扱わない．

#### 処理方針

コンフィグアーティファクトとは，デプロイ用設定生成処理によって生成される設定ファイルを指す．ターゲットパッケージのネイティブな設定ファイルと環境設定に基づき，デプロイ用ビルドの前に次のファイルを生成する．生成先は既知の規約とし，ファイルの所在を戻り値に含めてビルド・デプロイへ持ち回らない．

| 存在するファイル           | 生成するファイル                |
| ------------------ | ----------------------- |
| `.env.development` | `.env.production`           |
| `wrangler.jsonc`   | `wrangler.deploy.jsonc` |

設定値と優先順位は[環境設定の設計](./configuration-design.md)に従う．既存の`.env.production`はマージせず，生成結果で置き換える．ファイルの存在そのものは禁止しない．デプロイ用ビルドは生成した`.env.production`を使用する．`.env.production.local`やプロセス環境変数の存在は検知せず，その取り扱いは各パッケージのビルドマネージャに委ねる．

設定はchannelから導出されるprofileを基礎として生成する．previewでは，staging profileを基礎に，次の規則でWorker名と接続先を反映する．

- preview Worker名は，`[base worker名]-preview-[PR番号]`とする．
- 接続先のパッケージが今回のターゲットパッケージに含まれる場合は，同じPRのpreviewへ接続する．
- 接続先のパッケージが今回のターゲットパッケージに含まれない場合は，stagingへ接続する．
- 接続先の判定には，過去に作られたpreviewが存在するかどうかを用いない．
- D1やR2などのリソースは，stagingのものを再利用する．

設定生成に失敗した場合は，後続処理を中断し，結果を通知する．

### 4. ビルド

#### 入出力

| 区分     | 内容                                                      |
| ------ | ------------------------------------------------------- |
| 入力     | ビルドパッケージ一覧，対象commitのソースと依存関係，生成したコンフィグアーティファクト，ビルドの実行条件 |
| 成功時の出力 | パッケージごとのビルド成功                               |
| 失敗時の出力 | ビルドに失敗した理由と，取得できたパッケージごとの結果・詳細 |
| 副作用 | 各パッケージの所定の場所にビルド成果物を生成・復元する |

ビルドの取りまとめ処理はパッケージごとの結果を収集し，進行管理処理へ返す．通知上の「対象外」「未実行」は，レポート生成処理が計画と実行結果から判定する．ビルドパッケージが空の場合は，本処理を行わない．

#### 処理方針

設定生成後，ビルドパッケージを指定してTurborepoへビルドを依頼し，実行結果を収集する．Turboは各パッケージの通常の`build`スクリプトを実行し，依存パッケージのビルド順序と実行を管理する．`build`スクリプトのないパッケージはビルドの実行対象に含めない．ビルドに失敗した場合はデプロイへ進まず，結果を通知する．

デプロイ固有のビルドスクリプトは要求しない．各パッケージは通常の`build`を提供し，`tsc -b && vite build`や任意の前処理を伴うパイプラインなど，実装方法は各パッケージに委ねる．パッケージ側はデプロイのmodeやchannelを知る必要がない．デプロイ用設定の生成方法や成果物に関する知識は`tools/deploy/`に集約する．

Viteでは通常の`vite build`によるproduction modeで，生成した`.env.production`を使用する．デプロイのprofileとViteのmodeは分離する．

| channel | profile | Vite mode |
| --- | --- | --- |
| preview | staging | production |
| staging | staging | production |
| release | release | production |

ビルドキャッシュを利用する場合，ソースコード，依存関係，ビルドに影響する設定，生成した`.env.production`，必要な環境変数をキャッシュ判定に含める．復元する成果物は，各パッケージのビルド結果に応じて定義する．ビルド成果物の所在は既知の規約とし，戻り値として持ち回らない．

既存の`app-build`から設定生成とビルドを分離する際は，`tsc -b`，Viteビルド，Wranglerのdry-runなど，従来行っていた処理を棚卸しし，必要な処理を欠落させない．

## 実行フェーズ

### 入出力

| 区分         | 内容                                                       |
| ---------- | -------------------------------------------------------- |
| 入力         | 計画で決定した順序付きデプロイパッケージ一覧と，準備フェーズで生成したデプロイ用設定・成果物．必要な準備が成功していることを前提とする |
| パッケージごとの出力 | デプロイの成否，取得できた場合のアクセス先，失敗時の理由と取得できた詳細                         |
| 集約結果       | 全体の成功・一部失敗・失敗と，各パッケージの結果                                 |

コマンドの起動や出力の取得に失敗した場合も，確認できた事実とエラーを保持する．デプロイの成否を確認できていない場合は，成功として扱わない．デプロイパッケージが空の場合はコマンドを実行せず，対象がないことを通知に引き渡す．

### デプロイの実行

準備がすべて成功したら，各デプロイパッケージで次を実行する．

```sh
wrangler deploy --config wrangler.deploy.jsonc --minify
```

計画フェーズで決定した順序に従い，パッケージを逐次デプロイする．個別デプロイが失敗しても，残りのパッケージのデプロイを続ける．

`wrangler deploy`の終了コードが0なら成功，それ以外は失敗とする．アクセス先URLの取得は成功の必須条件とせず，取得できた場合にのみ結果へ含める．Service Bindingの参照先が存在しないことによる失敗も通常のデプロイ失敗として扱い，循環を解消する自動リトライや多段階デプロイは導入しない．計画時に循環の警告があっても，Wranglerが正常終了すれば成功とする．

各実行の成否と，取得できたアクセス先を収集する．一部が失敗した場合も，各パッケージの結果を保持し，全体の成功・一部失敗・失敗を区別する．

Wranglerの出力から必要な情報を取り出す責務は個別デプロイの実行処理に置く．デプロイの取りまとめ処理は各パッケージの結果を収集・集約して進行管理処理へ返し，進行管理処理が他の処理結果とともにレポート生成へ渡す．

## 通知フェーズ

### 入出力

| 処理                              | 入力                                                   | 出力                            |
| ------------------------------- | ---------------------------------------------------- | ----------------------------- |
| Markdownレポート生成（`tools/deploy/`） | channel，対象commit，開始時のmode，確定済みの計画情報（最終mode・フォールバック理由・警告を含む），各処理・パッケージの保持済み結果，中断・異常の情報 | 生成したレポートファイルの所在，または生成できなかった理由 |
| GitHubへの掲載（`.github/`）          | レポートファイル，通知先の情報，Workflowのステップ結果・ログへのリンクなど            | 掲載の成否と，失敗した場合の理由              |

デプロイ処理全体の成否と，レポート生成・掲載自体の成否は区別する．デプロイ処理の失敗を報告するレポートの生成に成功した場合も，デプロイ処理の失敗は維持する．

### 結果の収集とレポート生成

`tools/deploy/`は，保持した処理結果からMarkdownレポートを生成する．このレポートはGitHubの通知先に依存しないものとする．

レポート生成処理は，進行管理処理から受け取った計画と実行結果をもとに，パッケージごとの通知用の表を組み立てる．各処理の対象集合と実行状況を照合し，「対象外」「未実行」を判定する．テストの「テストなし」や，合格・不合格・実行エラーなど，実行側で得た結果はそのまま利用する．CLIエントリーポイントは表の組み立てや状態の判定を行わない．

レポートにはchannel，対象commit，開始時のmode，処理全体の結果，中断した場合はそのフェーズと理由を含める．modeが変わった場合は最終modeとフォールバック理由を含める．計画時の警告もデプロイの成否と区別して報告する．

計画上の対象パッケージと、実行結果が取得できたパッケージをキーとして次の内容を表にまとめる．

| タスク   | 報告内容                               |
| ---- | ---------------------------------- |
| テスト  | 成功・失敗・未実行・計画上の所属．結果を再利用した場合はその旨 |
| ビルド  | 成功・失敗・未実行・計画上の所属                      |
| デプロイ | 成功・失敗・未実行・計画上の所属．取得できた場合はアクセス先         |

「未実行」はタスクが前段の失敗およびスクリプトの不在などによって実行されなかった場合を示す．

計画上の所属とは，そのパッケージが計画フェーズのどの集合に所属するかを示す．以下の基準で上から順に判定し，最初に一致した分類を使う．

1. ターゲットパッケージに所属する場合，"対象"とする
2. 影響パッケージに所属する場合，"影響下"とする
3. 上記のいずれでもない場合，空とする．

テストの失敗には，表とは別に失敗内容の詳しい報告を付す．テストの不合格と，起動や結果取得などの実行エラーを区別して示す．長大な出力は実行ログに残し，レポートでは原因を確認できる要約を示す．

計画中の失敗で影響パッケージやターゲットパッケージが未確定の場合も，判明したエラーを報告する．デプロイ対象がないことは，テスト結果や処理全体の成否とは分けて報告する．ターゲットパッケージが空でもテストを行った場合は，その結果を省略せず，テスト失敗を「対象なし」で上書きしない．影響パッケージとターゲットパッケージがともに空の場合は，失敗と混同せず，テスト・デプロイ対象がない旨を報告する．

### GitHubへの掲載

`.github/`側はMarkdownレポートを受け取り，channelに応じた場所へ掲載する．

| channel               | 通知先                  |
| --------------------- | -------------------- |
| `preview`             | 対象PRのコメント            |
| `staging` / `release` | WorkflowのJob Summary |

PRの特定，コメントの投稿，Job Summaryへの書き込み，Workflowのログへのリンク，スラッシュコマンドのusageの付加は，`.github/`側の責務とする．

### 途中で失敗した場合の通知

進行管理処理は，想定する失敗が結果として返された場合，それまでの結果を集約し，レポート生成処理を呼び出してから最終結果をCLIエントリーポイントへ返す．CLIエントリーポイントは，返された最終結果に対応する終了コードで終了する．想定外の例外による異常終了時は，レポート生成を要求しない．

Workflowの通知ステップは`if: always()`を用い，先行ステップが失敗した場合も通知を試みる．レポート生成前の異常終了などでファイルがない場合は，`.github/`側で取得できるステップの結果とログへのリンクを使い，最低限の通知を行う．

updateのデプロイ失敗・一部失敗・途中終了などでデプロイ先の状態が不確かな場合は，通知に手動の全件デプロイによる復旧を案内する．具体的なWorkflowの起動方法は`.github/`側で付加する．レポートがない場合も，取得できるステップ結果から該当すると判断できれば，同じ案内を最低限の通知に含める．ただし，取得できるステップ結果から案内できる場合でも，内容の解析に複雑な処理を要する場合はこれを行わない．

## クリーンアップ

### 入出力

| 区分 | 内容                                                       |
| -- | -------------------------------------------------------- |
| 入力 | クローズされたPRの番号                                             |
| 出力 | 列挙した削除対象とWorkerごとの削除結果，全体の成功・一部失敗・失敗，対象がなかったこと，列挙・削除に失敗した場合の理由と取得済みの結果 |

### 削除対象と実行

PRがクローズされたときに，そのPRのレビュー用環境のために作成したリソースを削除する．

デプロイ先で実在するWorkerを列挙し，名前が`-preview-[PR番号]`で終わるWorkerをすべて削除する．削除対象は，現在のソースや最後のデプロイ計画だけから求めない．過去のデプロイで残ったWorkerや，デプロイの途中終了で残ったWorkerも対象に含める．パッケージ削除やWorkerのbase名変更によって残ったWorkerも，同じサフィックスに基づいて削除する．

削除対象の列挙に失敗した場合は処理を中断する．個別Workerの削除に失敗しても残りの削除を継続し，各Workerの結果を保持して全体の成功・一部失敗・失敗を集約する．削除対象が存在しない場合は正常終了とする．

D1やR2など，stagingの共有・既存リソースは削除しない．

クリーンアップは，同じPRのpreviewデプロイと同じconcurrency groupを共有し，`queue: single`で直列化する．実行中の処理は完了させる．

updateでは，デプロイ中に不要なWorkerを自動削除しない．不要なWorkerの撤去はデプロイとは独立した処理で扱う．

## 実装時に確認する事項

設計上の入出力と実行方針は本文のとおりとし，以下は実装時に確認・具体化する．

- Turboのテスト実行では，並列度制限と失敗時の継続オプション，タスク依存関係を確認し，影響パッケージだけを逐次実行して失敗後も継続する契約を満たす．結果取得方法は，キャッシュヒット時も同じ結果形式を満たすよう選ぶ．
- PRへのpushと`/preview`コメントではイベントと実行refが異なるため，GitHub Actionsのrefによるアクセス範囲の制約下でPR単位のキャッシュを共有できるか検証する．共有できない場合は保存・復元方式を調整する．
- 現在の`turbo.json`で無効になっている`build`キャッシュを有効化する場合は，本文の入力と成果物に合わせて入出力設定を見直す．

## 別途設計する事項

updateで不要になったWorkerを撤去する処理の実行契機と削除対象の判定方式は別途設計するため，ここではスコープ外である．
