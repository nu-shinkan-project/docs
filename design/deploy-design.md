# デプロイ設計

## このドキュメントの目的

このドキュメントは，[デプロイのメンタルモデル](./deploy-model.md)をもとに，自動デプロイの設計を定めます．用語はメンタルモデルに従います．GitHub Actions で受け付けたデプロイ要求について，対象選定，設定・成果物の生成，反映，結果通知までの責務と入出力を扱います．現在の実装がすべてこの設計を満たすことを意味しません．

環境変数，`deployment.yaml`，設定の優先順位は，[環境設定の設計](./configuration-design.md)に従います．

## 実現方針

トリガーフェーズとオーケストレーションをGithub Workflow (YAML) が担い，Githubなしに説明できるデプロイ概念はtools/deploy配下の開発用スクリプトとして実現する．

## 複数コンポーネント間での通信

複数モードでのソースコードの共有，責務の分割による粗結合のために，複数のコンポーネントをオーケストレーションで束ねる場合は，コンポーネント間の通信はファイル契約によってなされるものとする．つまり，前段のコンポーネントがjsonファイルを出力し，後段のコンポーネントはjsonファイルを受け取る．

ただし，エラー通知に関しては，開発用スクリプトは標準エラー出力に吐き出し，Workflowがこれを解析する．
高度に構造化されるべきエラー報告に関してはこの限りではない．jsonファイルを出力しても構わない．
解析しやすいように標準エラー出力を工夫することは妨げないが，あからさまにGithubを意識した構成にはしないこと．
（Github Workflow以外は，Githubで使われることを知ってはならない．）

## トリガーフェーズ

`release`タグの付け替えがあったとき，`release`チャンネルのデプロイをトリガーする．デプロイ対象は新しくタグがついたコミット．
`staging`タグの付け替えがあったとき，`staging`チャンネルのデプロイをトリガーする．デプロイ対象は新しくタグがついたコミット．
いずれも，基本的には(`update`, `diff`)モードで，差分の基準は，タグを付け替える前のコミットである．
ヒストリーが直線的でない，遡っているなどの理由で差分の検出が不可能な場合は(`update`, `full`)モードにフォールバックする．

releaseデプロイ，stagingデプロイのタグの付替えを伴わない手動トリガーがあったとき，それぞれのチャンネルのデプロイを`full`モードで行う．
デプロイ対象のコミットは，その時点でタグ`release`, `staging`が付されているコミットである．

PRがpushされたとき，`preview`チャンネル，(`review`, `diff`)モードのデプロイをトリガーする．差分の基準はPRのマージ先(BASEブランチ)である．
PRに`/preview <パッケージ名...>`形式のスラッシュコマンドのコメントが投稿されたとき，(`review`, `manual-pick`)モードのデプロイをトリガーする．

(`update`, `diff`)モードでは，tools/deploy/update.tsをエントリーポイントとして呼び出す．
この際，次の情報をコマンドライン引数として受け渡す．

- channel
- 比較元commit hash
- デプロイ対象commit hash

(`update`, `full`)モードでは，tools/deploy/full.tsをエントリーポイントとして呼び出す．
この際，次の情報をコマンドライン引数として受け渡す．

- channel
- デプロイ対象commit hash

(`review`, `diff`)モードでは，tools/deploy/review.tsをエントリーポイントとして呼び出す．
この際，次の情報をコマンドライン引数として受け渡す．

- channel
- 比較元commit hash (PR BASE)
- デプロイ対象commit hash (PR HEAD)

(`review`, `manual-pick`)モードでは，tools/deploy/manual-pick.tsをエントリーポイントとして呼び出す．
この際，次の情報をコマンドライン引数として受け渡す．

- channel
- デプロイ対象パッケージのリスト
- デプロイ対象commit hash

## 計画フェーズ

計画フェーズでは，それぞれのエントリーポイントが，ターゲットパッケージ，ビルドパッケージ，デプロイパッケージを収集する．
ターゲットパッケージのうち，現状ではvite.config.tsを持つものがビルドパッケージであり，apps/ 配下にあるものがデプロイパッケージである．
ターゲットパッケージからビルドパッケージ，デプロイパッケージを取得するロジックは，エントリーポイント間で共通化できる．

selection sourceごとの収集ロジックも共有化できる．
selection sourceが`full`であるとき，apps/ packages/ 配下の全パッケージをターゲットパッケージとする．

selection sourceが`diff`であるとき，apps/ packages/ 配下の全パッケージのうち，コミット間の差分が存在する全パッケージをターゲットパッケージとする．
pnpm-lock.yamlの更新，差分の計算不可（履歴の分岐や遡り）の際にはselection sourceが`full`のロジックに内部でフォールバックする．

selection sourceが`manual-pick`であるとき，`manual-pick`に指定されたパッケージのうち，
実際にapps/ packages/ 配下に存在するパッケージをターゲットパッケージとする．
`manual-pick`に存在しないパッケージが指定された場合はデプロイワークフローを中断し，存在しないパッケージのためにデプロイに失敗した旨とスラッシュコマンドのusageを通知する．ただし，存在しないパッケージが確認された直後に中断するのではなく，すべてのパッケージの存在性をまとめて検証して，まとめて報告する．

さらに，purposeがreviewである場合は，connectionグラフに基づくビルド・デプロイ対象の拡張（connection-hydration）を行う．
connection-hydrationでは，各パッケージの[deployment.yamlで定められるconnectionとreviewEntryの設定](configuration-design.md)
を元にconnection-graphを構築する．connection-graphは利用元(Webなど)が始点，利用先(API)が終点となるグラフである．
なお，グラフの構成において，存在しないパッケージの指定，自己ループが発生した場合は，単にそれらの辺は無いものとして扱う．
こうして構築したconnection-graph上で，reviewEntry（がtrueであるような）パッケージ A, ターゲットパッケージ Bをとり，AからBへのすべてのパスを考える．
そのいずれかのパスに含まれるパッケージを，レビューパッケージという．
すべてのreviewEntryパッケージとターゲットパッケージの組み合わせでレビューパッケージを計算してユニオンをとり，最終的なレビューパッケージとする．
hydrationを行った後は，計算したレビューパッケージをターゲットパッケージとして用いる．（つまり，レビューパッケージという語彙はhydration中のみに用いるのであって，以降は元のターゲットパッケージを上書きして取り回す）

## 準備フェーズ

1. syncを実行して，環境変数やWorker名を最新化する．
2. ターゲットパッケージについて，testスクリプトがあれば実行する．テストに失敗したパッケージがあれば，デプロイフローをここで中断し，その旨を通知する．ただし，テストに失敗した直後に中断するのではなく，すべてのパッケージのテストは行った上で結果をまとめて通知する．
結果の成否によらず，テストの結果は，パッケージとその依存関係に変化がなければ再利用できるように，ファイルに出力する．
3. テストを通過したら，ターゲットパッケージについて，コンフィグファイルの生成を行う．コンフィグファイルの生成は，
パッケージ内に存在するネイティブなコンフィグファイル`.env.development`, `wrangler.jsonc`の存在の有無で判断する．
`.env.developent`が存在すれば，`.env.deploy`を，`wrangler.jsonc`が存在すれば，`wrangler.deploy.jsonc`を生成する．
失敗した場合は即座にワークフローを中断し，通知する．
4. コンフィグファイルの生成後，ビルドパッケージについてビルドを行う．ビルド方法は設定ファイルの有無から判断する．
たとえば，`vite.config.ts`が存在すれば`vite build --mode deploy`を実行する．
（現状では，これ以外にビルドするべきパッケージの構成は存在しない．）
失敗した場合は，即座にワークフローを中断し，通知する．

責務分割のため，ターゲットパッケージに定められたスクリプトには一切依存せず，tools/deploy内で完結する．デプロイアーティファクトに関する知識を各パッケージに漏らすべきではないという判断のためである．

## 実行フェーズ

デプロイする．各デプロイパッケージで，`wrangler deploy --config wrangler.deploy.jsonc --minify`を実行する．
結果を解析して，デプロイの成否，アクセス先リンクを抽出し，すべてのデプロイの結果をjson形式のファイルとして出力する．

## 通知フェーズ

ターゲットパッケージごとに，

- テストの結果（存在しないなら，その旨を報告する．）
- ビルドの成否（ビルドパッケージでない・試みられていないなら，結果なし．）
- デプロイの成否（デプロイパッケージでない・試みられていないなら，結果なし．成功ならアクセス先リンク．）

を通知する．ターゲットパッケージをキーとしたテーブルを通知すれば良い．

なお，テストの失敗においては，表とは別に詳しい報告を付す．

ターゲットパッケージが存在しない場合は，その旨を通知する．
